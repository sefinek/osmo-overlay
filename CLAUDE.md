# CLAUDE.md

Guidance for Claude Code in this repository. Only what the code doesn't say by itself.

## What this is

OsmoOverlay burns a telemetry HUD (speed, heading, tilt, sun, stats) onto footage from DJI Osmo Action and Insta360 cameras. The picture is re-encoded once with the source's own codec and settings, so user-facing text never claims "no quality loss" for a render - only the stream-copy Tools may.

Projects in `OsmoOverlay.slnx` (net10.0):
- `Core` - everything that isn't one camera's: telemetry processing, SkiaSharp overlay renderer, ffmpeg pipeline, preview, 360 reframing, `ICameraFormat`. Depends on no GUI/CLI and no camera.
- `Cameras.Dji`, `Cameras.Insta360` - one camera each, implementing `ICameraFormat`. They see Core's internals (`InternalsVisibleTo`).
- `Cli` (thin wrapper around `RenderJob`), `Gui` (Avalonia), `Tests` (MSTest), `Build` (release packaging, references nothing).

Shared settings (framework, company, `Version` - the one place to bump it, output paths) live in `Directory.Build.props`; a csproj holds only what's its own. Release builds treat warnings as errors (NuGet audit warnings excepted), so keep the build at zero warnings. Package versions live only in `Directory.Packages.props` (central package management), each written out - Visual Studio's NuGet manager replaces a `$(property)` in a Version with the number it updated to, so a shared property drifted from its packages; a family's packages (Avalonia, SkiaSharp) carry one version instead (`PackageVersionsTests`). Dependabot proposes updates weekly, each family in one PR (`groups` in `dependabot.yml`).

## Build and test

- `dotnet build OsmoOverlay.Core|Cli|Gui` - build Core/Cli alone when verifying logic (faster, doesn't need the GUI closed).
- `dotnet test --project OsmoOverlay.Tests` - MSTest.Sdk on Microsoft.Testing.Platform (`global.json` opts in; required on .NET 10). Pure logic with synthetic data, never a real recording. The implicit CodeCoverage extension is versioned by `MicrosoftTestingExtensionsCodeCoverageVersion` in the csproj - a `PackageReference Update` has no effect on it.
- Anything touching ffmpeg/ffprobe is verified by a real build plus the CLI on a real file; visual changes by rendering `OverlayRenderer` to a PNG via SkiaSharp.
- Release packages: `dotnet run --project OsmoOverlay.Build` (`-- --help`). Per RID, self-contained and framework-dependent; zip on Windows, tar.gz elsewhere (written by the tool so executables keep +x); Inno Setup 7 installer for win-x64/arm64. FFmpeg isn't bundled.
- CI (`.github/workflows`): every push to `main` and every PR builds the `.slnx` in Release and tests on Windows/Linux/macOS with the SDK from `global.json`. Release is run by hand and creates a **draft** `v<Version>`; the tag exists only once the draft is published. Workflows carry no comments - reasoning lives here.

## Installer and updates

- Installer script: `OsmoOverlay.Build/Installer/OsmoOverlay.iss`. `AppId` never changes. Per-user install (`PrivilegesRequired=lowest`, no override), `WizardStyle=classic dark` (keep). Dependencies are the app's job, not the installer's. The Inno download in `release.yml` is pinned by SHA-256 - update URL and hash together.
- In-app update (`Core/Updates/AppUpdates.cs`): latest GitHub release, installer asset checked against its SHA-256, run with `/UPDATE /SILENT`. Only for a copy installed by the setup (`CanUpdateInPlace`); other copies get the release page.
- These three must match: `AppGuid` in the .iss, `AppUpdates.InstallerGuid`, and the mutex (`AppUpdates.MutexName` = the .iss `AppMutexName`).
- The `.ovproj` association is written twice with the same keys: the installer (`AssociateProjects` task, checked by default, kept across `/UPDATE` because the old uninstaller deletes the keys) and Settings' Interface tab (`ProjectFileAssociation`). `ProjectProgId` in the .iss and `ProjectFileAssociation.ProgId` must match, as must the command line (`"exe" "%1"`).
- GUI: `UpdateChecks` is the one check (app + dependencies), run once at startup; only Settings' "Check for updates" reruns it. A declined app version is stored in `OverlaySettings.SkippedAppUpdate`.

## Dependencies (external)

- FFmpeg is required, as `ffmpeg`/`ffprobe` and as shared libraries matching `FFmpeg.AutoGen`'s major (the preview decodes in-process). `ffmpeg`/`ffprobe` are started from the install the libraries come from (`DependencyChecker.FromFfmpegLibraryFolder`, via `ProcessHelper`), so one FFmpeg install is used everywhere. On Windows the installer uses `Gyan.FFmpeg.Shared`.
- `exiftool` is optional (`ExternalTool.IsOptional`): the startup prompt appears only when a required tool is missing; optional ones are installed from Settings' About tab or `OsmoOverlay.Cli --install-dependencies`.
- Install/update never go past `ExternalTool.SupportedMajorVersion`: winget gets an explicit `--version`, a newer major is only reported.
- Windows can't upgrade FFmpeg while its DLLs are loaded - Update closes the app, upgrades in a PowerShell window and restarts it (`DependencyInstaller.UpgradeNeedsRestart`).

## Telemetry

- **Camera formats.** Core knows no camera. An `ICameraFormat` detects its files, extracts telemetry, says which way gravity pulls in its accelerometer's axes (`Gravity`, null = unknown) and copies its own metadata into a render. Formats are registered in both `Program`s (`CameraFormats.Register`, tried in order). `FileSummary.CameraFormatId` is part of the cache - never change a released one. A new camera = a new project, nothing changes in Core.
- Telemetry frames keep the camera's own accelerometer axes. Core does the physics once for every camera (`CameraTilt`, G-meter, `HorizonLeveling`); nothing in Core reads `AccelX/Y/Z` as a direction. `OverlayAvailability` turns widgets off when `Gravity` is null.
- Extract telemetry only through `TelemetryExtraction.ExtractCombined`; don't add other call sites.
- **Cache**: `FileSummaryCache.FormatVersion` **must be bumped by 1 whenever extraction/processing logic changes**, or a stale entry hides the change.
- `TelemetryProcessor.Process`: windows and EMA time constants are in **seconds**, not samples (independent of sampling rate). Speed prefers the receiver's `GpsSpeedMs` over differentiating position. Distance advances in 1 s steps and skips a step the receiver measured as standing still at both ends (`StandstillKmh`), so a wandering fix at a stop isn't travel; without `GpsSpeedMs` every step counts. Gradient is over `GradientWindowMeters` of distance centered on the frame (shared with `KeyMoments`) - a per-second slope was GPS altitude noise.
- **Speed correction** (`OverlaySettings.SpeedCorrectionPercent`, `SpeedCalibration`): a global percent for a GPS that reads low, applied in `TelemetryProcessor.Process` to `DerivedFrame.SpeedKmh` only (tilt, heading, distance keep the measured values), so every consumer agrees. Cached summary frames are derived without it (and without GPS smoothing) - `SpeedCalibration.Apply` where they're used (key moments); the Telemetry card's max speed is processed like the preview and corrected (`ShowMaxSpeedInfo`), so it matches the widgets. Edited with one `SpeedCalibrationEditor` in the first-run `WelcomeWindow` (`WelcomeShown`) and Settings' Speed tab; the preview reopens on a change. `SpeedCalibration.PercentFor` rounds down to 0.1%, and the calculator compares a real speed with the measured one (before any correction, so its result doesn't depend on the one already set) - from the loaded recording its cruising speed, `SpeedCalibration.CruisingSpeedKmh`, never a top speed: the shown speed is the receiver's per sample and jitters, and over a long ride even a few seconds' maximum is where the GPS read highest (on a real ride: 25.8 km/h held for 3 s against a ~22 km/h cruise).
- **Tilt**: `CameraTilt` over `Gravity` - roll = asin(g_x), pitch = -asin(g_z), with the vehicle's own acceleration (from GPS) taken out. DJI's gravity is (-AccelY, -AccelZ, -AccelX), Insta360 X4's is (AccelZ, -AccelX, AccelY) - all verified empirically on real recordings. Don't change axes, signs or compensation without similar verification.
- **No GPS fix / no GPS time**: `OverlayDataRequirements` forces off widgets that need missing data at every point a layout reaches the renderer. `DateTimeText`/`UtcTimeText` fall back to the container's `creation_time` (the camera's own clock, flagged in the GUI).
- **No telemetry at all** (a file no camera format knows): the preview still plays it with stand-in frames (`PlainRecordingFrames`) and an empty layout; render stays disabled.
- **Multi-file recordings**: files are joined back to back, each placed after the previous files' *frames* (`VideoSegments.Join`: frames / fps), never their container duration, which runs on to where the audio ends (+26 ms on a real Osmo Action 6 split) and put later files' telemetry and preview frames 1-2 frames behind the render's. The preview's video joins by `PlaybackSegment.FrameCount`, its audio by `DurationSeconds` - as the render does. A file starting over 2 s after the previous one ended by the GPS clock gets `TelemetryFrame.StartsAfterGap`, and smoothing/windows/routes don't run across it. Without GPS time the files stay joined.
- **GPS clock**: `ExtractCombined` turns the receiver's whole seconds into one clock running with the video (`ApplyGpsClock`): started from the first file with GPS time (counted back to the first frame, sub-second from the first tick), continued across splits (each file's own ticks land a frame or two off - a measured -37 ms step at a join), restarted only after a stop. So every frame of a recording with any GPS time has `GpsTimestamp`, and `RecordedAtUtc`, the time widgets and the sun all read one clock.

### DJI Osmo Action (`Cameras.Dji`)
- Telemetry is a `djmd` protobuf stream, decoded by hand (`DjiMetaTelemetryParser`, field mapping in its XML comment; verified byte-for-byte against exiftool). Its samples are read straight from the MP4 sample table (`ReadTrackSamples`, parallel reads - an SSD serves them at once) instead of ffmpeg demuxing the whole file; byte-identical to ffmpeg's extraction on real files, which stays the fallback. `SampleTimeSeconds` is deliberately `index / fps`, as exiftool computes it.
- `ExifToolTelemetry` is the fallback only when the native decoder throws; the choice is in `DjiOsmoFormat.ExtractTelemetry`. Both paths share `GpsForwardFill` - keep it one file. It takes the altitude only with a fix (the camera writes 0 m without one).
- The GPS time string is a whole hour off UTC (Osmo Action 6, Poland, summer time: exactly 60 min behind `creation_time`, file name and timecode on every recording with a fix; the camera's clock confirmed right). `GpsClockZone` moves it onto the camera's clock when the two differ by whole quarter hours (+-2 min drift), and the GUI logs it (`FileSummary.GpsClockShift`). Never shift it unconditionally - in winter the offset may be 0.

### Insta360 (`Cameras.Insta360`)
- `.insv`/`.lrv` telemetry is a trailer after the last MP4 box (ffprobe doesn't see it); `Insta360TrailerParser` documents the layout. No GPS read yet. CameraInfo is unavailable (no ISO/color temperature).
- A 360 recording becomes a flat 16:9 view (`Core.Reframe`, `FisheyeProjector`): the same C# projector for preview and render (ffmpeg's v360 rebuilds its map on every change - 5x slower). Lens FOV 190 was found on a real X4. `HorizonLeveling` keeps the horizon level from the accelerometer; another model may need its own `Gravity`.
- The render of a 360 recording is composed in `RenderJob.ProduceComposedAsync`; ffmpeg only encodes it and takes the sound from the source files.

## Overlay

- `OverlayRenderer` is data-driven: it draws the active preset's `OverlayElement`s. Add a new `OverlayElementType`'s default position/visibility to `OverlayPreset.CreateDefault` - with every widget turned on, none may cover another (`CreateDefault_NoWidgetCoversAnother_AllOfThemOn`), so one that's off by default goes into a free spot. The default preset is read-only in the GUI.
- Presets have no migrations or backfills for older formats (pre-1.0) - don't add any.
- A widget's `X`/`Y` are in the 3840x2160 reference space, not the video's pixels, so a preset fits every resolution and aspect ratio; each axis scales on its own (`OverlayElementBounds.ToPixels`/`ToReference`), sizes use the one `GetScale`. The renderer and the editor convert at the edge - the editor itself works in video pixels. `CreateDefault` is resolution-independent.
- Widget boxes for hit-testing come from `OverlayRenderer.MeasureElement`, not estimates; `OverlayElementBounds.GetBounds` is only a fallback.
- `BeginElement` (`OverlayRenderer.Animation.cs`) is the one place each widget's draw is set up (anchor, scale, slide, fade); widgets draw around (0, 0) and never do their own Save/Translate/Scale. Timing (`AppearAtSeconds`, in/out animation) is generic for every type: the GUI uses one `ElementTimingEditor` and one `ElementStyleEditor`. The trip progress bar alone can instead wait for the ride to first reach a speed (`ShowFromSpeedKmh`): that moment replaces its appear time (`OverlayRenderer.SpeedGateSeconds`), and the GUI shows it locked in the timing editor (`LockAppear`) and as the clip's start on its layer (`ClipAppear`).
- Layers (`OverlayLayers`): the renderer never reads a layer - the layout's order is the draw order. Mute/solo go through `OverlayLayers.Drawn`. Widget times are on the output timeline (after cuts); the timeline shows the recording, so convert with `OutputTimeline.ToRecordingSeconds`/`NearestOutputSeconds`. The layer timeline's first column (track names, the ruler's slot holding the new-layer button) is `LayerTimeline.HeaderWidth` wide, set in `WireLayers` - not the width in the XAML.
- Drawing a frame must be idempotent: a widget's value may depend only on the frame (and the set of frames), never on which frames were drawn before it - a paused or re-composed still draws the same frame again. That's why the G-meter's smoothing is precomputed per frame (`GMeterDeltas`) instead of an EMA updated while drawing.
- Overlay text style (`DrawOutlined`: a thin outline, nothing else) is deliberate - don't change it without an explicit request. It had its own blurred drop shadow too; under the widget's shadow the two read as a smudgy 3D glow, so the widget's shadow is the text's only one.
- Widget shadow (`OverlayRenderer.Shadow.cs`, `OverlayElement.Shadow*`, on by default, centered (offset 0 - the user wants CSS's `0 0 10px`, not a 3D drop), radius 10 for text, 10-20 for the bigger widgets = how far the soft edge reaches, three sigmas of the blur): an image filter on the widget's layer casts it like CSS's drop-shadow, from the widget's own pixels, under it. Only a widget on a translucent panel (`ShadowStyle.BehindPanel`) casts it from its *footprint* (every drawn pixel made solid, so the panel casts a full shadow) and cuts it out under it, so the panel isn't darkened twice - done for every widget, that cut-out left the video showing through text edges' partial pixels without the shadow, a light seam (`Shadow_ReachesUnderTheWidgetsEdge_NoLightSeam`). It is the only shadow a widget has: off means none. `OverlaySettings.DisableShadows` turns every shadow off - preview, snapshot (`OverlayCompositor.SnapshotShadows`) and render - keeping the widgets' values and locking their shadow controls (`ElementShadowEditor.SetLocked`). A shadowed widget (`IsShadowed`: on, opacity above 0) is recorded once in `DrawWidgets` and played back, its layer sized from the recording's bounds (round widgets draw directly: known size, and the trail reads the canvas matrix); hover and selection use `MeasureElement`, which never includes the shadow. Shadows are ~85% of the overlay's drawing time at 4K (measured ~56 of ~66 ms a frame); the preview can leave them out (`OverlaySettings.PreviewShadows`, `PreviewDrawsShadows`, `OverlayRenderer.DrawShadows`), a render and the snapshot draw them unless `DisableShadows`. So when any visible widget is shadowed, `DrawWidgets` records each widget in layout order (drawing reads and updates the renderer's state, one at a time), rasterizes them in parallel into bitmaps sized by `BeginElement`'s `drawn` - not the picture's CullRect, which cut off the blur's outer edge - and draws them on in order: the same picture to +-2 a channel (`ParallelWidgets_DrawLikeWidgetsDrawnStraightOn`), 4K 36 -> 16 ms a frame, a whole render 20 -> 29 fps.
- Panel fill: `IPanelElement` (`PanelColor`, `PanelOpacity`, default 55% black) on the widgets drawn on a panel; opacity 0 is the Ring look for any of them. The Gui's `WithPanel` lists them, as a record can't be copied through an interface - add a new panel widget there too. "Apply to all" copies shadow/panel/font+colors to the rest of the preset (`MainWindow.WidgetAppearance.cs`).
- The overlay is drawn premultiplied (Skia's unpremultiplied path is ~10x slower) and converted to straight alpha in `BgraAlpha`.
- The summary's max G is the smoothed one the widget shows (`DerivedFrame.SmoothedGForce`), not a single raw sample (6.5 G jolts on a ride). Statistics (`TripStats`): nothing counted across a cut or a gap, moving time from 3 km/h, elevation with a 3 m hysteresis (the plain sum gave 3-10x too much).
- Map tile servers: one list (`MapProviders`), picked per consumer (`MapWidgetElement.MapProviderId`, `OverlaySettings.RouteIntroMapProvider`) through the one `MapSourcePicker` control. What's shared lives once in `OverlaySettings`: API keys per `KeyGroup` (all CARTO styles share one key) and the custom server. `MapSources` turns an id into a URL/credit; the renderer fetches one mosaic for the first visible Map widget, so other Map widgets draw from it. Each provider carries its terms (`MapTerms`, checked against the providers' own on 2026-10-04, shown in the picker): the default `satellite` is Esri World Imagery with its key, else Esri's public service - one source, never another provider's key - the user's choice over GUGiK/EOX, whose imagery they found too poor (`MapSources.Resolve`); tile.openstreetmap.org and Stadia are left out on purpose; Esri's public service is listed with its terms as they are (`MapUse.NotAllowed`); and so are Mapbox (video only incidentally, promoting your app), Google (no caching, promo videos up to 30 s) and HERE's satellite (online viewing only). Esri World Imagery goes through an ArcGIS Location Platform key and is never stored on disk (`CacheDays` 0 - its terms forbid storing Data). Two "best available" picks, `satellite` and `streets` (Esri Navigation with the key, else Esri's public Street Map); a map with no provider of its own shows `OverlaySettings.DefaultMapProvider` (null = satellite). The widget's picker and the first-run window's Map step show and set that one style: a best-available pick in the widget becomes the default (the widget's own id stays null), a single provider is the widget's own and leaves the Map step's styles unticked, saying so; ticking a style there gives the widget back to it (`ClearMapWidgetProviders`). The Map step also has a live preview of both styles (fetched like a render's map) and takes the Esri key (same `MapApiKeys`). ArcGIS Static Basemap Tiles are 512 px a zoom lower: a template with `{hz}/{hx}/{hy}` makes `MapTileFetcher` cut this tile's quarter out of one shared download. A provider needing a key fetches nothing without one (`MissesApiKey`) - the widget shows its placeholder. The credit is its own widget (`MapAttributionElement`), drawn only with a map on screen; where a map's terms say `WhileMapVisible` it's drawn the whole time, hidden or missing from the preset (then at the default spot, `MapCreditAt`), and the GUI locks its timing. The watermark is a widget too (`WatermarkElement`, centered on X): `OverlaySettings.ShowWatermark` stays the one switch (the default preset can't hide a widget), the widget only places, styles and times it (default: top center under the Text slot - the bottom center is the progress bar's, which may show from the start - for the first 6 s, fading out); a preset without one gets it at the default spot, and the route overview card shows it in its own bottom-right corner (`DrawWatermark`).
- Settings: `OverlaySettingsStore` (`settings.json`) holds cross-preset state; presets are one file each in `%LOCALAPPDATA%\OsmoOverlay\presets`. `SettingsWindow` is one `Load(OverlaySettings)`/`Apply(OverlaySettings)` pair - a new setting goes there, and `MainWindow.OnSettingsClick` saves once.
- Interface scale: Linux uses `AVALONIA_GLOBAL_SCALE_FACTOR`; on Windows/macOS every window's content sits in a `LayoutTransformControl` and popups use the overlay layer. Code counting device pixels uses `UiScale.DeviceScaling`, not `RenderScaling`.

## Projects

- `OverlayProject` (`.ovproj`, JSON, `Format` bumps only when old files can't be read): recordings, output path, cuts (frames), 360 view, preview frame and the overlay. ## Live preview

- `PreviewPlayer` decodes in-process through FFmpeg's shared libraries (`LibavLoader`; major must match `FFmpeg.AutoGen`), GPU first. **No ffmpeg-process fallback on purpose** (0.3-1.7 s per seek); missing libraries are a dependency problem.
- The overlay is composited on the CPU on purpose (~1 ms). All use of `OverlayRenderer` (not thread-safe) goes through the compositor's lock; decoding runs outside it.
- Frame buffers come from one `FrameBufferPool` per recording. A still's `Bgra` is valid only during the `FrameReady` callback; a played frame belongs to the caller until `PlaybackFrameSource.Release`.
- Presentation is driven by the display on the compositor's render thread (`VideoView` -> `TakeDueFrame`), not by a timer, `Task.Delay` or `RequestAnimationFrame` (uneven, late frames measured). Each stopped playback logs a summary to app.log - the first place to look when playback isn't smooth.
- `PlaybackClock` follows the audio device (smoothed against its stepping); a stopwatch without audio. Two sessions never share the decoder or the device (`_sessionsStopped`).
- Seeks: latest wins; keyframe while dragging, exact on release. Cancellation is a cooperative `null`, not an exception.
- `PreviewFrames.IndexAt` is the one rule for "which frame is on screen", shared by the decoder and the GUI's `CurrentFrame()`.
- Full screen preview (`MainWindow.PreviewFullscreen.cs`): the viewport (`PreviewViewport`) is moved into a window and back, never mirrored - a played frame goes to exactly one `VideoView`, and a `VideoView` starts empty when attached, so playback pauses for the move and the frame is shown again after it. The monitor is `OverlaySettings.PreviewMonitor` (`MonitorChoice`).
- Second screen (`MainWindow.SecondScreen.cs`, F9, `OverlaySettings.SecondScreenEnabled`): a `SecondScreenWindow` shows the log (every line goes through `AppendLog`/`AppendLogLine`/`ClearLogPanels`, which feed both panels) and takes the viewport while the preview plays, the same move as the full screen's, so `_movingViewport` keeps the pause/restart of a move from starting another one. Never together with the full screen preview.
- In the GUI the overlay element list is **copy-on-write** (`ReplaceActiveElements`) because the compose thread may be enumerating it. Dragging an element pauses playback.

## Render

- **Range and cuts**: `RenderPlan.Resolve` gives whole kept frames from `RenderOptions.RangeStart/End` and `CutOuts`. The GUI has only cuts (I/O marks, X/Delete, `CutList`), no From/To; the CLI has `--from/--to/--cut/--frames`. Telemetry follows the cut video (`OutputTimeline.MapFrames` processes the whole recording once, then keeps kept pieces and re-sums distance). Routes cross a cut as `RouteJoin` says.
- **ffmpeg** (`FfmpegPipeline`): one piece = `AddSourceInputs` (plain `-ss`, plus a concat input only if it runs into later files); several pieces = `AddCutInputs` (each trimmed to its exact frame count, joined with the concat filter, audio re-encoded to AAC). Verified frame-exact on real files. Don't switch video to concat's `inpoint`/`-ss` (stuck frames) or drop the audio list's `-itsoffset` (audio leads by ~0.3-0.8 s). Each piece's video gets a one-frame time base and timestamps from the frame number (`settb=den/num,setpts=N`): a piece running into the next file comes out of the concat filter in 1/1000000 with a gap at the join, which `xfade` rejects (different time bases) or, rebased to AVTB, turns into a frame too many or too few. A single piece over several files gets the same (`FrameNumbered`): the concat demuxer starts each later file where the previous container ends (+26 ms past its last frame), so overlay paired every frame after a join with the pipe's next one and `shortest=1` cut as many off the end (synthetic two-file test: 237 of 240 frames, mispaired; renumbered, all 240 exact). Verified frame-exact on real files across a file join. The overlay's `scale` (BGRA to YUV) runs with `threads=0`: swscale is single-threaded by default and was the graph's slowest stage at 4K (31 -> 67 fps, output bit-identical). The main picture's format is set before the overlay, not negotiated: hardware decoding gives p010, which overlay can't take, and ffmpeg picked yuva420p10 for it (an alpha plane added and blended every frame) - 40 -> 47 fps for a 4K 10-bit graph, output bit-identical. Sound across files: a camera split cuts the audio a little after the picture (+26 ms, then +7.5 ms on a real Osmo Action 6 recording), and both run on unbroken - the picture's clock in djmd steps one frame across a join, no sound repeats (high-passed correlation), and the whole recording's audio ends 21 ms after its picture, under one AAC frame. So the sound's timeline is the files joined by container duration (the full render's concat input, the preview's `PlaybackSegment.DurationSeconds`, `VideoSegments.LocateAudio`), and a piece starting in a later file opens its sound where that is (`SoundFor`) - its picture's time in the file put the sound 26/34 ms early in the 2nd/3rd file. Verified 0.00 ms against the full timeline's sound on real files: a range in the 2nd file, a range across the 2nd-3rd join, cut pieces in both; the 1st file's paths are unchanged. A partial render doesn't copy the camera's data tracks.
- **Cut transitions** (`CutTransition`, per cut): a fade through black or white, half out of the part before the cut and half into the one after, both inside the kept frames - so the frame count, telemetry and overlay timing never change, and the overlay itself isn't faded. `RenderPlan.Resolve` puts it on `RenderPiece.TransitionIn/Out` (none for a cut at the very start/end). Flat recordings fade in the ffmpeg graph (`fade`/`afade` in `AddCutInputs`), pictures made in C# (360 render, preview) through `CutTransitionFade`, the same curve. Crossfade/wipe/push (`CutTransition.Overlaps`) instead show the end of the earlier part and the start of the later one together and so shorten the output: `RenderPiece.OverlapIn` (at most half of the shorter part) is the frames a piece shares with the one before it, `RenderPlan.TotalFrames` and `OutputTimeline` count them once, telemetry through the overlap is the earlier part's (`MapFrames` skips the later part's head). ffmpeg joins such pieces one after another with `xfade`/`acrossfade` (the rest with `concat`), the 360 render with `CutTransitionBlend` (same directions and progress i/n as xfade, checked against ffmpeg's output). The preview doesn't blend: it plays the earlier part through the overlap and then goes on after the later part's head (`NextKeptStretch`), so its time stays the render's. Verified frame-exact on a real file (the 360 path only by tests).
- **Output parity**: the default export matches the source 1:1 (constant bitrate at the source's rate, no B-frames, GOP/level/tier read from the source - its first file's, the one encoded like, so only that one gets the GOP and tier probes (`SourceProbe.Probe(encoderDetails)`), `hvc1`, exact frame count via `overlay=...:shortest=1`, `creation_time` + timecode). Export options may deviate only when the user picks a non-default value - never change the defaults. Settings' resolution (short side, never upscaled), codec (H.264 is always 8-bit) and 8-bit change the written stream through one place, `OutputVideo.For` (unset = the source's own `VideoInfo`, so the default graph and args stay as they were): the encoder is picked for it (an encoder chosen for the source is dropped if it doesn't write its codec - `FfmpegPipeline.Encodes`), the overlay is drawn at its size, the source is scaled to it (`ResizeFilter`), the bitrate shrinks with the pixel count (x1.5 for H.264 from HEVC), and a changed size or codec leaves level/tier to the encoder.
- **Encoders** (`FfmpegPipeline.SelectVideoEncoder`): the graphics card's first - NVENC, then (Windows only) AMD's AMF and Intel's Quick Sync - else x264/x265. Each is probed with the render's own `AddVideoEncoderArgs` at the output's size, so a probe passes only where the render will; only a success is cached. AMF and Quick Sync take over the decoder's device and fail on another vendor's (NVIDIA + AMD laptop: "AMF failed to initialise on the given D3D11 device"), so they get their own D3D11 device (`EncoderDeviceArgs`): their vendor's card with the most memory of its own, by its DXGI index (`GpuAdapters.Pick` - a laptop's dedicated Radeon RX or Arc, not the integrated one of the same vendor that ffmpeg's `vendor_id` would take first), `vendor_id` only without DXGI. Hardware decoding runs on that device (`HwDecodeArgs`); RenderBenchmark, the first-run window's decoding check and the load before a render use the same card. Settings' preset stays NVENC's p1-p7 scale (`OverlaySettings.NvencPreset`), mapped by `PresetName` (AMF speed/balanced/quality, Quick Sync veryfast-veryslow). Both want p010le/nv12. AMF verified on a real 4K 10-bit recording (Radeon 610M: profile, level, tier, GOP, frame count, `hvc1`, colors and timecode as the source, ~92 Mbps average against 90; `-enforce_hrd`/`-filler_data` changed nothing), also through cuts with transitions; Quick Sync is untested - its level and tier are left to the encoder. The CLI's `--encoder` forces one.
- **Disk space**: before a render the GUI checks the output's drive (`RenderDiskSpace`): the source's bytes per kept frame, scaled by the output's bitrate over the source's, twice (`Mp4FastStart` may copy the finished file once more), and asks before going on with less.
- **Camera metadata**: ffmpeg can't mux `djmd`/`dbgi`, so `ICameraFormat.CopyMetadata` does it after ffmpeg at the box level (`Mp4CameraMetadata`, `Mp4FastStart`). The serial number lives only in the first djmd sample (protobuf f1.1.5) and in udta `©uid`; unless explicitly kept (default: no) both are removed.

## Tools (`ToolsWindow`)

Standalone utilities, unrelated to the render flow: `ColorTagFixer` (remux to bt709 tags, no re-encode), `MetadataStripper` (share-safe copy, verified against the source before it replaces `.partial`), `CameraAudioConverter` (Osmo's `.AAC` to WAV/M4A, verified by sample MD5; no MP3 on purpose), `CompareVideosWindow` (hand-built table, no DataGrid dependency), data folder and cache management. Cache entries (summaries, waveforms) unused for `OverlaySettings.CacheCleanupDays` (default 30, 0 = never; Settings' Behavior tab) are deleted at startup (`FileSummaryCache.DeleteUnused`); a read marks an entry used (`MarkUsed`, its modification time). Entries are Brotli-compressed JSON (`.json.br`; an hour at 59.94 fps: 212 MB plain, 35 MB compressed), streamed, never read into a string; the version and file stamps are read from the entry's start first (`ReadHeader`), so a stale or foreign entry is never deserialized whole. A plain `.json` entry from before is dropped as stale. Dependency versions are shown in Settings' About tab (`DependencyStatusRows`), not here.

Performance test (`BenchmarkWindow`, Core `RenderBenchmark`): opened from Tools' card, Settings' Rendering link and the first-run window's "Your computer" step, all through `MainWindow.ShowBenchmarkAsync`. No file is picked: it makes its own sample - `SampleSeconds` copied out of the loaded recording (the camera's own bitstream; a generated clip decodes on the CPU 3-4x more easily than a camera's, measured 105-139 against 37 fps, even with grain), or without one a generated 4K 10-bit HEVC clip, on which decoding isn't compared. It measures decoding on the GPU and the CPU, the overlay with and without shadows at the render's and the preview's size, handing frames to ffmpeg, the encoders (the graphics card's at p1/p4/p7 - `PresetName` - and the CPU one, through the render's own `FfmpegPipeline.AddVideoEncoderArgs`), ffmpeg as a whole and a short render the way `RenderJob` runs one - the layout with a sample route drawn, over the pipe, through `FfmpegPipeline.FilterGraph` and the encoder in use (only no sound or metadata), its drawing stopped when ffmpeg stops (a producer waiting on a full channel nobody reads hung the test). ffmpeg's input options go before any `-map`: an output option ahead of a second input makes ffmpeg exit at once. Frames a second are steady state, from ffmpeg's periodic `-progress` reports only (the final one comes after it flushed and closed). `RenderBenchmark.Advise` suggests only decoding and the preview's shadows - the encoder preset changes the file's quality, so it's shown, never suggested. An applied suggestion is saved at once; nothing else is - a run under load would skew `RenderSpeedHistory`, which only real renders feed. Everything is measured for the output Settings ask for (`OutputVideo`), the Map widget's tiles fetched first. Results depend on what else uses the GPU: a game running halved the hardware decode in testing - so the load is sampled first (`BenchmarkLoad`: CPU from `GetSystemTimes` or `/proc/stat`; the GPU's graphics and compute (not its video or copy engines, as nvidia-smi counts it), its video encoder and decoder and the other programs encoding on it, on Windows from the `GPU Engine` counters of the card the encoder runs on - any vendor, matched by LUID through DXGI, this app's own process left out, `WindowsGpuLoad` - elsewhere from `nvidia-smi`), shown with a warning, and decoding isn't suggested when it was busy. While the test runs the window shows the same numbers live, once a second (`LoadMonitor`, this app's own use counted). Each ffmpeg step runs several times (after a warm-up), the compared ones taking turns going first, and a result is the median with the runs' range (`BenchmarkStat`, unstable above 10%); the overlay is timed frame by frame early, middle and late in the recording (median, p95), the preview through `RenderOnto` as it draws. A suggestion to switch decoding needs every run of the faster side above every run of the other (`ClearlyFaster`). `Bottleneck` names the slowest stage in use and how close the short render came to it - ffmpeg as a whole among them (decoding, the render's own `FfmpegPipeline.FilterGraph` and the encoder at once, a still overlay instead of the pipe): on a real 4K recording it ran at 36 fps against 147 decoding and 49 encoding alone, so it, not the encoder, is usually what holds a render back; on a quiet computer the short render reached 73% of it. Before a render or a green screen the GUI samples the same load (`ConfirmComputerNotBusyAsync`, ~1 s) and asks when it would slow the encoder in use (`BenchmarkLoad.SlowsRender`: for a GPU encoder its card and encoder, and the CPU above 60% since the overlay is drawn there; the CPU above 40% for x264/x265 - looser than the benchmark's, so a browser or GeForce's background recording doesn't ask every time). The first-run window's "Your computer" step (`HardwareCheck`, also with a Performance test button) rates the system, CPU threads, RAM, graphics cards (virtual monitors left out), the encoder a 4K 10-bit render would pick, hardware decoding and the output folder's free space; thresholds live in `HardwareReport`. Hardware decoding is a real try - a tiny 10-bit HEVC clip decoded through the platform's method with its frames kept in GPU memory: `-hwaccel` alone falls back to the CPU silently, and `-hwaccels` lists what's compiled in (vaapi on Windows), not what works.

## Localization

- **Polish is the source language, English is the default.** Wording is written and polished in Polish first (natural word order, no calques from English, lowercase "ty/twój" in UI); the English text is translated from it. English stays the neutral resource only because it's the fallback for every non-Polish system. When changing a text, change the Polish one first, then bring the English in line.
- English (neutral) and Polish. GUI texts in `Gui/Resources/Strings.resx` + `Strings.pl.resx` (class `OsmoOverlay.Gui.Strings`), Core/camera texts that reach the user in `Core/Localization/CoreStrings*.resx` (internal). The classes are generated by MSBuild (`StronglyTyped*` metadata in the csproj), there's no Designer.cs. XAML uses `{x:Static local:Strings.Key}`, so the class must stay public.
- A new user-facing text goes into both files at once; `ResourceParityTests` checks keys, `{n}` placeholders and plural shape. Plurals are one resource with forms split by `|` (English `one|other`, Polish `one|few|many`), read through `Plural.Format`.
- The language is `OverlaySettings.UiLanguage` (null = system's, else English), applied once in the GUI's `Program.Main` as the UI culture only - `CurrentCulture` (number/date formats, ffmpeg args) is untouched. A change restarts the app like the interface scale. The CLI forces English.
- Not translated: the overlay's own texts (content of the video, incl. default widget labels), file-log-only `AppLogger.Info` lines, ffmpeg/parser exception details, `DeveloperWindow`, the PowerShell update script, the `.ovproj` ProgId description (written by the installer too), the performance test's window title ("Benchmark", a name - the heading inside is translated).

## Conventions

- Real recordings embed GPS tracks and the camera serial number. Never commit one (`.gitignore` excludes them) and never paste their telemetry into anything shared externally.
- `Core` folders (namespace stays `OsmoOverlay.Core`): `Editing` (cuts, history, project file, markers), `Rendering` (render job, plan, output timeline), `Recordings` (file summary, its cache, telemetry extraction), `Support` (process/file helpers, time text), plus the feature folders. Tests mirror them.
- `Gui` folders: `Windows` (`Main` is the main window's partials - the shell, `Preview` for playback/timeline, `Editing` for the overlay, layers and cuts), `Controls`, `Resources` (icons, palette), `Helpers`, `Updates`, `Native`. The namespace stays flat (`OsmoOverlay.Gui`) whatever the folder, so `x:Class` and `xmlns:local` don't change when a file moves.
- `ProcessHelper.CreateHidden` for every external tool (ffmpeg/ffprobe/exiftool) - never a hand-built `ProcessStartInfo`.
- GUI colors only in the palette: the color keys in `Resources/Themes/*.axaml` (Dark is the default, each theme defines every key) and the brushes in `App.axaml` (`{StaticResource ...Brush}`, C# through `Palette`), never a hex literal. `AppThemes` switches themes by recoloring the brushes in place, the accent gradient's stops included; shared classes (`card`, `hint`, ...) are global there; `ScrollViewer` has `AllowAutoHide=False` globally. The overlay's own render colors are content, not UI.
- Fluent's own colors (dropdowns, menus, flyouts, item states) are replaced by aliasing its resource keys to palette brushes in `App.axaml`, not by fighting its selectors. Before restyling a Fluent control, read its template in the Avalonia source for the exact version (`src/Avalonia.Themes.Fluent/Controls`): part names, what a nested theme ignores (the spinner's `RepeatButton` binds no `CornerRadius`), and an inner part painting square over a rounded parent.
- `BrushTransition` from `Transparent` (#00FFFFFF) to an opaque color passes through a light grey. A control with a transparent background either hovers to a translucent white (`SubtleFillBrush`, as `addedWidgetAction`, its `:pressed` too - the global one is opaque), fades a layer's opacity (`SidebarItem`) or has its `Transitions` off.
- XAML carries no comments - reasoning lives here.
- GUI icons only in `Icons.axaml`, shown with `IconView` (not `PathIcon`, not Unicode glyphs): a filled shape on a 16x16 grid (never stroked, inside 0..16), which `IconView` scales and fills with the surrounding text color, so it follows hover/disabled without extra styles. A hole is a subpath running the other way under nonzero fill (`F1`).
- The editor's hover outline (`Rectangle.hoverOutline`) marches its dashes only while shown, so a hidden one costs no redraws; dash lengths are in stroke widths (4 + 3 = a period of 7).
- `AngleMath` is the only place for angle conversions.
