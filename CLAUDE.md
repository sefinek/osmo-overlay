 # CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OsmoOverlay burns a telemetry HUD (speed, heading, tilt, sun, stats) onto footage from DJI Osmo Action cameras without any loss of source quality/codec (see README.md - re-encoding in DJI Mimo degrades quality; this application does not).

Five projects in one `.slnx` (net10.0):
- `OsmoOverlay.Core` - all the logic: telemetry extraction, telemetry processing, overlay renderer (SkiaSharp), ffmpeg pipeline, video preview. No dependency on GUI/CLI.
- `OsmoOverlay.Cli` - thin console wrapper around `RenderJob`.
- `OsmoOverlay.Gui` - Avalonia, overlay editor + live preview + running the render.
- `OsmoOverlay.Tests` - MSTest unit tests of Core's pure logic (see Build).
- `OsmoOverlay.Build` - release packaging tool, no reference to the others (see Build).

Everything the projects share - target framework, company/copyright, `Version` (the one place to bump it), output paths, `DebugType` - is in `Directory.Build.props`; a csproj only holds what's its own (output type, names, `Title`/`FileDescription`, references).

## Build

```
dotnet build OsmoOverlay.Core
dotnet build OsmoOverlay.Cli
dotnet build OsmoOverlay.Gui
```

Building the whole `.slnx` also works, but build Core/Cli separately when you're only verifying logic changes - it's faster and doesn't require closing the GUI.

Release packages: `dotnet run --project OsmoOverlay.Build` (`-- --help` for options: `--rid`, `--flavor`, `--version`, `--output`, `--skip-tests`, `--no-archive`). Runs the tests, then publishes GUI + CLI together into one folder per RID (win-x64/arm64, linux-x64/arm64, osx-x64/arm64 by default), each both self-contained and framework-dependent, into `artifacts/` (git-ignored): zip for Windows, tar.gz for Linux/macOS (written by the tool itself so the executables keep +x - a zip made on Windows carries no Unix modes), plus a SHA256SUMS file. `README.md` and `LICENSE` go into every package's root folder. For win-x64/win-arm64 self-contained it also builds an Inno Setup 7 installer (`OsmoOverlay-<version>-<rid>-setup.exe`) from `OsmoOverlay.Build/Installer/OsmoOverlay.iss`, compiled with ISCC from the published folder before it's zipped (values passed as `-D` defines; ISCC found in Program Files/PATH or via `--iscc`, skipped with a note when missing or with `--no-installer`). The script's `AppId` GUID must never change - Windows matches upgrades and the uninstaller by it. Per-user install by default (`PrivilegesRequired=lowest`, all-users selectable), 64-bit setup (`SetupArchitecture=x64`), `WizardStyle=modern dynamic windows11`. At `ssInstall` it runs the previous version's uninstaller (`UninstallString` from HKCU/HKLM `Uninstall\{AppGuid}_is1`, `/VERYSILENT`) so files the old version had and the new one doesn't don't stay behind; with `/UPDATE` it skips the tasks page, keeps the desktop shortcut if there was one (checked in `InitializeSetup`, before that uninstaller deletes it), waits up to 15 s for the app's `AppMutex` and starts the app again when done.

App updates (`OsmoOverlay.Core/Updates/AppUpdates.cs`): the latest GitHub release (`/releases/latest`, so no prereleases/drafts) is compared with the assembly version. On Windows the release's `-win-<arch>-setup.exe` asset is downloaded to the temp folder, checked against its SHA-256 (the asset's `digest`, or the release's `SHA256SUMS.txt`) and started with `/UPDATE /SILENT /NORESTART /LOG=` (log next to app.log), then the app shuts down. That only happens for a copy the setup installed and that runs from its install folder (`CanUpdateInPlace`: `InstallLocation` from the uninstall key vs `AppContext.BaseDirectory`) - a zip copy or dev build gets the release page instead. `AppGuid` in the .iss, `AppUpdates.InstallerGuid` and the GUI's mutex (`AppUpdates.MutexName`, taken in `Program.Main`) must match. GUI: `UpdateChecks` is the one update check - the app's release and every dependency's version together, run once at startup (after the missing-dependency prompt) and kept; Settings' About tab shows that result, and only its "Check for updates" starts a new one (`RefreshAsync`). Every check logs what it found. At startup a new app version is offered in a dialog (a declined one is remembered in `OverlaySettings.SkippedAppUpdate` and not asked about again), dependency updates are only logged; installing goes through `AppUpdateFlow`. On macOS the GUI is an `OsmoOverlay.app` bundle with the CLI inside `Contents/MacOS`. Every RID is cross-published from any host (no AOT); `AppendRuntimeIdentifierToOutputPath=true` is passed so RIDs don't share an intermediate folder. The .app isn't signed or notarized. FFmpeg isn't bundled - it stays an external dependency (see below). Linux-musl RIDs aren't in the defaults: ppy.SDL3-CS ships no musl build, so the preview would play silent there.

Unit tests: `dotnet test --project OsmoOverlay.Tests` (MSTest.Sdk on Microsoft.Testing.Platform - `global.json` opts `dotnet test` into it, required on the .NET 10 SDK). They cover pure logic only, with synthetic data - never a real recording: the djmd protobuf decoder (`Proto` in `DjmdBuilder.cs` writes samples per the parser's documented layout), telemetry processing, timecode math, render-range resolution, time text parsing, the cut output timeline (`OutputTimeline`: mapped frames, distance, kept stretches), `MetadataStripper.Verify` on hand-made ffprobe JSON, concat lists and segment lookup, gaps between files (detection by the GPS clock, nothing run across them), widget data requirements, route geometry across cuts, the speed color scale, `OverlayRenderer.SetFrames`, cut lists and timeline markers, playback plans (cuts, loops) and frame steps, `PlaybackClock` (fake audio device and wall clock through `IAudioClockSource`), the atempo chain, the waveform's dB scale, and winget's version list with the supported-major pick. Core exposes internals to them via `InternalsVisibleTo`. Anything touching ffmpeg/ffprobe (render, preview, stripping, audio conversion) is still verified by an actual build plus running the CLI against a real file, or rendering `OverlayRenderer` straight to a PNG via SkiaSharp (bypassing the GUI) for visual changes.

Real DJI Osmo Action MP4s embed GPS data and the camera's serial number directly in the file. Treat any such sample/test file as sensitive - don't paste its telemetry contents into anything shared externally.

External runtime dependencies: FFmpeg (required) as both `ffmpeg`/`ffprobe` on PATH (render, probing, the Tools) and its shared libraries in the major FFmpeg.AutoGen targets (the preview decodes in-process, see Live preview) - `ExternalTool.NeedsSharedLibraries` makes the dependency check count FFmpeg without loadable libraries as missing; on Windows the installer uses `Gyan.FFmpeg.Shared`, which provides both. `ffmpeg`/`ffprobe` are started from the install the libraries come from - their folder, or the `bin` beside a `lib` folder (Homebrew) - when it has them (`DependencyChecker.FromFfmpegLibraryFolder`, used by `FindExecutable` and `ProcessHelper`; it only looks the folder up via `LibavLoader.FindLibraryDirectory`, so the CLI doesn't load the libraries), so render, probing and preview run one FFmpeg install - a static Gyan build listed earlier on PATH is ignored. On Linux the libraries come from the system loader's paths and PATH decides. `exiftool` is an optional fallback (see below). `OsmoOverlay.Core/Dependencies/` checks/installs these in the GUI. Install and update never go past `ExternalTool.SupportedMajorVersion` (FFmpeg: the `FFmpeg.AutoGen` package major, `LibavLoader.SupportedMajorVersion`) - winget gets an explicit `--version` (the newest of that major from `winget show --versions`), and a newer major is only reported as not supported yet, never offered as an update. On Windows FFmpeg can't be upgraded while its DLLs are loaded (from the startup dependency check on; winget deletes the old version's folder), so the Update button closes the app and a visible PowerShell window runs the upgrade after it exits and starts the app again (`DependencyInstaller.UpgradeNeedsRestart`/`StartUpgradeAfterExitAsync`).

## Telemetry architecture (the most important part to understand)

DJI Osmo Action cameras embed an extra MP4 stream tagged `codec_tag` `djmd` containing protobuf-encoded data: GPS position/velocity, accelerometer XYZ, ISO, shutter speed, color temperature, device name. `SourceProbe.Probe` detects this stream (`SourceInfo.DjmdStreamIndex`/`HasDjmdTrack`).

**Primary path (native)**: `DjiMetaTelemetryParser` manually decodes this protobuf (varints, field/wire-type tags) with no protobuf library at all - the field mapping is documented in the XML comment at the top of the file and was verified byte-for-byte against exiftool across an entire real recording (zero mismatches, DJI Osmo Action 6). `SampleTimeSeconds` is deliberately `index / fps` (from ffprobe), not some raw timestamp in the stream - confirmed that exiftool itself computes it exactly this way too.

**Fallback**: `ExifToolRunner` (calls the external `exiftool`) - used only when the native decoder throws (a different model/firmware may lay out the stream differently) or when the file has no `djmd` stream at all. All the frame-extraction selection logic (native parser vs. exiftool fallback) lives in one place: `TelemetryExtraction.Extract`/`ExtractCombined`. Don't add other call sites that extract telemetry *frames* via `DjiMetaTelemetryParser` or `ExifToolRunner` directly - always go through `TelemetryExtraction`. The one standing exception is `ExifToolRunner.GetCameraModel`, called directly from `FileSummary.cs` when a file has no `djmd` track at all - it's a standalone metadata lookup, not part of the frame-extraction selection.

Both paths share `GpsForwardFill` (a dropped GPS fix in a tunnel/building should "hold" the last known position rather than snap to (0,0)) - if you change the forward-fill logic on one path, change it on both (through this shared file, don't duplicate it).

`TelemetryProcessor.Process` takes raw `TelemetryFrame`s and computes `DerivedFrame`s (speed, heading, gradient, cumulative distance, smoothed tilt/G-force). Key decisions:
- Time windows (speed/heading/gradient) and the EMA smoothing time constants are expressed in **seconds, not sample count** - behavior is meant to stay independent of the given file/camera's telemetry sampling rate.
- Speed prefers `GpsSpeedMs` from the GPS receiver itself (when available) over differentiating position - it isn't affected by GPS position quantization/lag.
- The tilt gauge uses `AccelY` (not `AccelX`) and is negated - confirmed empirically on a controlled test recording (isolated camera tilting, verified by extracting video frames and comparing them against the raw accelerometer values), see the comment next to `rawPitch` in `TelemetryProcessor.cs`. Don't change this without similar verification - it is not an obvious axis choice.

**Cache**: `FileSummaryCache` persists `FileSummary` as JSON to `%LOCALAPPDATA%\OsmoOverlay\cache\<sha256>.json`, keyed by full path + file size + modification time. `FileSummaryCache.FormatVersion` **must be bumped by 1 whenever telemetry extraction/processing logic changes** - otherwise a stale cache entry will silently return data computed with the old logic, making the change look like it didn't work.

**Multi-file recordings**: DJI Osmo Action auto-splits long recordings into consecutive files. `VideoSegments.ProbeAll` probes each input path into a `VideoSegment` (its own `SourceInfo` + `StartOffsetSeconds` on the combined virtual timeline). Files are joined back to back, but not every set of files is one split recording: `TelemetryExtraction.ExtractCombined` compares each file's start by the GPS clock (`GpsStartUtc`) with where the previous one ended, and a file starting over 2 s later (the camera was stopped; a real split measured 0.1 s off at most) gets `TelemetryFrame.StartsAfterGap` on its first frame - speed/heading/gradient windows, the smoothing, `SteppedDistances` and `GpsInterpolation` don't run across it, and the frame counts as `DerivedFrame.StartsAfterCut`, so the routes cross it as `RouteJoin` says (verified on real recordings: no false gap in a split recording, a 4-file set with 3 stops lost the 2.2 km ridden while the camera was off). Without GPS time there's nothing to compare, and files stay joined as one. `ConcatListWriter` writes the temporary ffmpeg concat-demuxer list files the render (`FfmpegPipeline`) stitches multi-segment recordings with; the preview opens each file itself (`LibavVideoSource`) and crosses into the next one at a file's real end.

**No GPS fix / no GPS timestamp**: many recordings (filmed indoors, GPS never acquired) have telemetry (accelerometer, ISO/shutter/color temp) but no position data at all. `TelemetryProcessor.HasAnyGpsFix`/`HasAnyGpsTimestamp` detect this; `OverlayDataRequirements.IsSupported`/`ApplyAvailability` force off (and the GUI greys out) any widget that needs data this file doesn't have, applied at every point a layout reaches `OverlayRenderer` (`RenderJob`, `PreviewPlayer`) so a widget checked against an earlier, GPS-capable file can't get burned into a render as a placeholder. `DateTimeText`/`UtcTimeText` are the one exception: with no GPS timestamp they still work off a fallback - `SourceInfo.ContainerCreationTimeUtc` (the MP4 container's own `creation_time` tag, written by the camera regardless of GPS) plus per-frame `SampleTimeSeconds`, threaded through as `FileSummary.ContainerRecordingStartUtc`. It's the camera's own clock, not GPS-synced, so the GUI flags it with a ⚠ next to the widget's checkbox instead of showing it as real GPS-recorded time.

## Overlay - data model and renderer

`OverlayRenderer` (SkiaSharp) is fully data-driven: it draws a list of `OverlayElement`s (type + X/Y + visibility) from the active `OverlayPreset`, instead of having positions hardcoded. Per-type sizes/radii live in `OverlayElementBounds` - the single source of truth shared by the renderer (drawing) and the GUI (hit-testing while dragging), so the two can't drift apart.

`OverlayPresetStore` holds multiple named presets, one file each in `%LOCALAPPDATA%\OsmoOverlay\presets\<id>.json` (a corrupt file only loses that preset), the active one's id in `settings.json`. The built-in `default` preset (`OverlayPresetStore.DefaultPresetId`) is read-only - the GUI locks editing while it's active, changes go through Duplicate. Both the GUI (editor) and the CLI/`RenderJob` (which has no editor) use the active preset whenever `RenderOptions.Layout` isn't explicitly supplied. Always add a new `OverlayElementType`'s default position/visibility to `OverlayPreset.CreateDefault` (the palette adds new instances from it). The app isn't released yet, so presets have no migrations or backfills for older formats - don't add any when the preset format changes.

`OverlaySettingsStore` persists cross-preset state to `%LOCALAPPDATA%\OsmoOverlay\settings.json` (`OverlaySettings`): active preset ID, watermark, GPS motion smoothing, live-preview quality, map tiles and attribution, the route intro card, route across cuts, the preview's own toggles (snap, grid, precise time, expanded timeline, mute/volume) and the export options (camera metadata parts, NVENC preset, hardware decoding, bitrate multiplier, fast start). Most of these can't be swapped on a running preview - `PreviewPlayer.SetShowWatermark` flips a draw-time flag and recomposes the last frame in place, but GPS smoothing and preview resolution are baked into the renderer/decoder at `OpenAsync` time, so the GUI reopens the whole preview for those (`MainWindow.ReopenPreviewAsync`, back at the same position) - after the settings dialog, or from the preview-quality picker on the left of the toolbar above the preview.

The speed gauge's scale is dynamic (`ComputeGaugeMaxSpeed` in `OverlayRenderer`) - it rounds up to the nearest ten based on the actual max speed observed in the given recording, not a fixed 60 km/h.

Every widget (regardless of type) can also have its own appear/disappear timing and transition, via `OverlayElement.AppearAtSeconds`/`DisappearAtSeconds`/`AnimationType`/`AnimationDurationSeconds` - null `AppearAtSeconds` means visible from frame 0, null `DisappearAtSeconds` means it never goes away, and the default `AnimationType.None` is an instant hard cut (so a preset with none of this set shows every visible widget for the whole recording). `OverlayRenderer.Animation.cs` (`BeginElement`/`ElementProgress`) is the single place `DrawWidgets` sets every widget's draw up through: it moves the canvas to the widget's anchor at `_scale * element.Scale` (every widget draws around (0, 0), none does its own Save/Translate/Scale), slides it, and fades it with a `SaveLayer` only while it's fading (`AlphaPaint`, the same paint the route-intro crossfade uses) - reusing the `FadeAlpha` the watermark's own fade relies on, rather than a separate mechanism. This is generic across all 15 `OverlayElementType`s, unlike the type-specific fields on `OverlayElement` (Label, Units, etc.) - so the GUI has one `ElementTimingEditor` UserControl (`{Widget}Timing` in each widget's settings panel in `MainWindow.axaml`): `Populate(element)` fills it, and every instance's `TimingChanged` goes to the single `MainWindow.OnElementTimingChanged` (`MainWindow.OverlayEditor.cs`). The text Style section (font/size/colors/outline) follows the same pattern with `ElementStyleEditor` (`{Widget}Style`, `HasAccentColor="True"` on the four `LabeledStatElement` widgets) and `MainWindow.OnElementStyleChanged`.

## Live preview (`PreviewPlayer` + Avalonia GUI)

`PreviewPlayer` is a facade over three parts: the open recording (its decoders, sound and `OverlayCompositor`), seeking, and playback (`PlaybackSession`, one per Play). `OverlayCompositor` owns the `OverlayRenderer` (not thread-safe, so everything touching it takes the compositor's one lock) and draws the overlay straight onto the decoded frame (`OverlayRenderer.RenderOnto` - source-over is associative, so it's the same pixels as blending a transparent overlay buffer, measured max 5/255 apart, without the full-frame clear and blend); a paused frame is kept clean as the still, which layout edits, a map landing or a setting compose again without decoding (`Recompose`). New cuts don't rebuild the renderer: `OverlayRenderer.SetFrames` swaps the telemetry and keeps fonts, paints and the map mosaic (`MapMosaicCoversRoute` - refetched only when the route now reaches past it), so the map doesn't flash its placeholder on every cut edit. The decoder works in-process through the FFmpeg shared libraries (NuGet `FFmpeg.AutoGen`, whose version must match the FFmpeg major - 9.x = avcodec-63; `LibavLoader` finds the DLLs on PATH/next to the app/Homebrew, checks the major, once per process). Every segment's file stays open, decoding runs on the GPU (CUDA first where there's an NVIDIA GPU, then D3D11VA/DXVA2, VideoToolbox, VAAPI, else multi-threaded software - measured on a 4K HEVC 10-bit Osmo file, RTX 4070: CUDA and D3D11VA give bit-identical frames, CUDA opens in 70 vs 145 ms and uses 1.65 vs 2.43 CPU cores for ~6% less throughput, 99 vs 106 fps; most of a frame is the 7-8 ms download of the 4K frame from the GPU, the conversion to BGRA at the preview size is ~0.9 ms and writes straight into the pooled buffer. Scaling on the GPU before the download was tried and left out: `scale_d3d11` fails on decoder textures in FFmpeg 9, and `scale_cuda` shifts red and blue by ~1.2 on average (up to 15) with every interpolation) and the decoder remembers where it is: the next frame just decodes on, a target up to 1 s ahead decodes forward without seeking, a one-frame step back decodes the frames before it in the same pass (`BackStepFrames` cache: up to 15, capped at ~160 MB - a full-resolution 4K preview frame is 33 MB). Measured on a 4K HEVC 10-bit Osmo file: open ~180 ms once, keyframe seek 15-19 ms, exact seek 16-160 ms, step forward ~10 ms, step back 0.2 ms from the cache (~200 ms on a miss), ~95 fps continuous.

There is deliberately no ffmpeg-process fallback: it costs 0.3-1.7 s per seek (process start + re-opening the file; Gyan's static 217 MB `ffmpeg.exe` alone takes ~800 ms to start, Defender scans it every launch). Missing or too-old libraries are a dependency problem the installer reports instead.

**Audio**: `LibavAudioSource` decodes the audio track in-process too (the demux/decode/seek part is shared with the video through `LibavStreamDecoder`), sample-accurate (a seek drops the samples before its target, a read stops exactly at a stretch's end - verified 240000/240000 samples for 5 s at 48 kHz), and `AudioOutput` plays it through SDL3 (NuGet `ppy.SDL3-CS`, natives bundled), whose audio stream converts to the device format. `PlaybackSession`'s audio feeder pushes the kept stretches back to back ~0.25 s ahead of the device, so cuts are skipped in the sound like in the render. `PlaybackClock` is where playback is on the play timeline (stretches back to back): while sound plays it follows the audio device (pushed - queued - device latency), and video follows it. The device takes sound a whole buffer (~10 ms) at a time, so its position alone moves in steps - `Now` runs on the wall clock and is eased toward the device's position (plus half a buffer, its average lag) at every reading, jumping only when 50 ms apart; unit-tested against a stepping fake device (frame-to-frame pace within 0.5 ms of even). Without an audio track or device, or once the sound runs out, a stopwatch.

**Playback pipeline** (`PlaybackSession`): decode thread -> compose thread -> presentation, joined by small bounded channels (2 decoded, 3 composed frames), plus the audio feeder. Presentation is driven by the display, on the compositor's render thread: `VideoView` (the preview's video control, a `CompositionCustomVisualHandler`) takes the frame due at every refresh from `PreviewPlayer.Frames` (`PlaybackFrameSource`, started by `PlaybackStarted`), uploads it to the GPU once (`ToTextureImage`, the pooled buffer lent to Skia without a copy and returned once Skia lets go of it) and draws it; the UI thread only gets the newest shown position, coalesced (`PlaybackFrameShown` - timeline, time readout, cut scrim). Taking frames from `TopLevel.RequestAnimationFrame` on the UI thread instead was measured at 90-180 uneven callbacks a second on 144/280 Hz displays and frames up to 57 ms late - every callback also laid out and committed the window. `TakeDueFrame` gives the next frame due by the middle of the refresh interval (measured between calls) - one new frame per refresh, a frame that missed its refresh by a little shown a refresh late rather than skipped, frames skipped only when later than 1.5 refreshes (or video frames) with the next one due too. Taking only the newest due frame instead dropped ~2 frames a second where frame and refresh rate nearly match or the UI thread came round a few ms late (measured 20 of 569 at 60 Hz with up to 6 ms of UI delay). No `Task.Delay` pacing and no timer. Each stopped playback logs a one-line summary to app.log (`PlaybackSession.Summary`: frames shown, skipped at the display, dropped late, decoded past, lateness, the refresh rate measured on the render thread) - the first thing to look at when playback doesn't look smooth. The decoder converts only a frame whose time hasn't passed yet: behind the sound, it first decodes past frames without converting them (`LibavVideoSource.PlaybackStream.Skip`), in batches proportional to how late it is, and asks again (`CatchUpFrames`; lateness is real time - at 4x a tenth of a second of play time is 25 ms). Skipping only part of the way and converting the next frame anyway had the compose thread drop what was just converted (398 frames in 22 s at 4x, ~3 s of wasted 4K downloads) and playback fell further behind after a few seconds. The compose thread still drops frames the sound already passed, as a safety net; without it an overlay slower than the frame rate puts playback behind for good and the picture froze while the sound played on. A speed change applies live (`SetRate`): the decoder's step changes from the next frame and only the sound restarts, from where playback is, at the new tempo (`PlaybackClock.RestartAudio`, `PlaybackPlan.StretchesFrom`). Measured end to end on the 4K60 file at 1280 px (a harness calling `TakeDueFrame` at 60 Hz): 1x 58 fps shown at 16.7-16.9 ms +- 0.3-1.9, 2x 60 fps +- 0.3, 0.5x 30 fps +- 0.4, all at the exact speed. 4x needs 240 decoded 4K frames a second, at the edge of what NVDEC does here: 50-54 fps shown, evenly, ~20 ms behind the sound, no gaps over 46 ms in 20 s through the heaviest part of the test file. Stopping a session awaits its threads and puts every buffer in flight back; the next session starts only after every earlier one stopped (`_sessionsStopped`), since two must never share the decoder or the device. Playback frames had the overlay drawn onto them, so stopping decodes the frame on screen again as the clean still. Mute is gain 0, not stopping the audio, so the clock never changes source mid-play. GUI: speaker + volume slider right of the toolbar (`MainWindow.Audio.cs`, key M), muted by default, mute and volume remembered in `OverlaySettings`.

**Preview tools** (toolbar above the preview, transport row): a status strip under the transport row, NLE style (`MainWindow.PreviewStatus.cs`; while the expanded timeline is shown it takes the compact timeline's place in the transport row, `SetTimelineExpanded`) - the recording's and the preview's resolution and frame rate, the frame at the cursor, and the preview's size on screen in physical pixels, with, while playing, the frames a second that reach the display (counted by `VideoView` where frames are drawn, over the last second, refreshed 4x a second; amber below 90% of `PreviewPlayer.PlaybackFrameRate`, what the speed calls for); H hides the overlay (`PreviewPlayer.SetShowOverlay`, a draw-time flag like the watermark); the camera button saves the frame on screen as a full-resolution PNG with the overlay as the render draws it (`RenderSnapshotPngAsync` - its own full-size decoder, so the preview isn't disturbed; ~0.8 s decode + ~1.2 s PNG encode at 4K); speed 0.25x-4x plus J/K/L (`SetPlaybackRate` - applies live, see the playback pipeline; above ~60 shown fps the decoder decodes every frame but converts only every Nth, `FrameStep`/`SkipNext`, measured 4.06x real time possible at step 4; the sound keeps its pitch through `AudioTempo` - FFmpeg's atempo, chained below 0.5x, verified 5 s in -> 2.47 s out at 2x - and the clock counts a second of it as `rate` seconds; no reverse play - 4K HEVC can't be decoded backwards at playback speed). Loop (Q, `SetLoop`): the In/Out selection or the whole recording, seamless - `PlaybackPlan.For` gives the rest from the position, then the range over and over, and the decoder and the audio feeder walk the same endless sequence. Up/Down jump between `TimelineMarkers` (ends, cut/selection edges, GPS loss). `PreviewTimeline` comes in two forms: the compact one in the transport row (`PreviewTimeline`, which holds the position everything reads; hidden while the expanded one shows), and, toggled by `MainWindow.SetTimelineExpanded` (toolbar button, remembered), an expanded one (`ExpandedTimeline`) in the log's place at the bottom of the window (the row shrinks to its height; shown only in `SummaryReady` with a telemetry recording loaded - with no file yet, while a summary or render runs, and after a render the log shows instead, the remembered choice coming back with the next summary). Everything describing the recording (duration, cuts, selection, GPS loss) goes to both through `MainWindow.Timelines`; the expanded one follows the compact one's position and hands its drags back to it with a ruler, a filmstrip (`TimelineThumbnails`: one keyframe per second, ~15 ms each, only what's visible, cached per recording as pixels, the timeline's bitmaps made from them capped at 240, least recently drawn dropped - keyframe requests decode ahead at most 6 frames, else a second of frames per thumbnail) and a per-channel waveform in dB, 48 dB down from the recording's own loudest peak (never below -72 dBFS, so a near-silent file's noise stays flat) so quiet camera audio still fills the track (`AudioWaveform`, 100 buckets/s, ~15 s in the background for 25 min, logged to app.log as `Timeline waveform`), wheel zoom around the pointer, Shift+wheel/scrollbar scroll, double-click on the ruler to fit, paging along while playing. The generators belong to the loaded recording (`MainWindow.TimelineTracks.cs`), so reopening the preview keeps them. The expanded timeline draws its static part (ruler, filmstrip, waveform, GPS loss) once into a `RenderTargetBitmap` (96 DPI, display scale pushed as a transform - at 96 * scale DPI only its top-left part got drawn, blown up) and redraws it only when the view or the generated content changes (generator reports at most every 100 ms; a tile whose thumbnail isn't generated yet shows the nearest generated one within its span, `NearestGenerated` - a zoom step moves every tile to another second) - per playback frame it draws that bitmap plus the playhead, cuts and selection; repainting everything each frame made playback stutter. The waveform is filled pixel by pixel into a bitmap (one column per device pixel) - as a geometry of one figure per column Skia took 250-370 ms to fill it at ~2000 px, on every scroll or zoom step. The waveform worker runs on its own below-normal-priority thread. Opening the cut editor expands the timeline. Cuts are edited on the timeline too: Shift+drag selects (the In/Out marks, live), a selection's or a cut's edge can be dragged (snapping to the playhead; a cut applies on release through `CutList.Resize`), a click selects the cut under it and Delete removes it (`CutList.Remove`; without a selected cut Delete cuts the selection out like X). Preview zoom (`MainWindow.PreviewZoom.cs`): Fit or a size relative to source pixels (100% = one source pixel per device pixel, `RenderScaling` included), Ctrl+wheel around the pointer, middle-button pan; the image is placed from `GetPreviewTransform`, which includes zoom and pan, so every editor overlay and hit-test follows. Toolbar and transport buttons aren't focusable and Space's key-up is swallowed after it toggled playback - otherwise a clicked button kept focus and Space re-clicked it (e.g. toggled the timeline).

`PreviewFrames.IndexAt` is the one rule for "which frame is on screen at this position" (first frame at/after it, quarter-frame slack) - shared by the decoder and the GUI's `CurrentFrame()` (frame stepping, cut marks), so they can't disagree by a frame.

Access modes:
- **Seek** (`RequestSeek`): latest wins, no debounce - an idle player decodes right away, while a decode runs only the newest request waits (a timeline drag shows frames as fast as they decode). The GUI asks for `SeekAccuracy.Keyframe` while the timeline is being dragged and the exact frame on release (`EndScrubDrag`). A newer seek doesn't cancel the running decode; `Play`/`Close` do (`CancelSeeks`, plus a generation counter so a late result isn't shown). Cancellation is a cooperative check returning `null`, not `OperationCanceledException` - a superseded seek is expected, not exceptional.
- **Dragging an overlay element** (`SetLayout`): no decoding - it swaps the renderer's layout and composes the still again (`OverlayCompositor.Change`). While playing there's no still (`ClearStill` at Play), the played frames show the edit.
- `OpenAsync` drops what it opened if a newer open/close overtook it (`_openGeneration`); `Close` disposes the recording on the thread pool once its session stopped (disposing the decoder waits for a decode still running).
- Decoding (seeks and playback) runs **outside** the compositor's lock; only drawing the overlay takes it, and a published frame is handed to the GUI outside it too, so a slow decode or the GUI's copy never blocks the UI thread's edits or the compose thread.

The overlay stays composited on the CPU on purpose: measured 1.2 ms to render all 15 widgets at 1280x720 (drawn straight onto the frame, no separate blend) - a separate GPU overlay layer isn't worth its threading complexity. Proxy media (a lighter copy for exact ~5-10 ms seeks) was also considered and left out for now: the in-process decoder's worst case (~160 ms exact seek) is what NLEs without proxies show on 4K HEVC.

Frame buffers are recycled through one `FrameBufferPool` per open recording, shared by the decoder, the compositor and playback, instead of allocated per frame - a played frame is the decoded buffer itself, the overlay drawn onto it. So `ComposedPreviewFrame.Bgra` passed to `FrameReady` (stills only) is only valid during the callback (`VideoView.ShowStill` copies it); a played frame from `PlaybackFrameSource` belongs to the caller until `PlaybackFrameSource.Release`; a still goes back to the pool when the next one replaces it.

In the GUI (`MainWindow.axaml.cs`), the overlay element list is edited via **copy-on-write**: every change (dragging, a visibility checkbox) builds a new list (`ActiveElements.ToList()`) and swaps the reference on the preset (`ReplaceActiveElements`), instead of mutating the existing list in place - because the compose thread may be concurrently enumerating that same list inside `OverlayRenderer.RenderOnto()`. Dragging an element **pauses playback** if it's currently running (`OnOverlayCanvasPointerPressed`).

## Render range and cuts

What gets rendered is a `RenderPlan` (`RenderPlan.Resolve`): the From/To range minus any cut-out parts, as the kept pieces in order, whole frames on the combined timeline. Set via `RenderOptions.RangeStartSeconds/RangeEndSeconds/CutOuts` (CLI: `--from/--to/--cut a-b`; times parsed/printed by `TimeText`). The GUI has no frame limit; the CLI has `--frames`.

The GUI deliberately has no From/To - a From/To range (what stays) next to cuts (what goes) confused users. There you only mark what gets removed, NLE style: I/O mark the first/last frame of a selection (both included; a missing side means the start/end of the recording), X/Delete cuts it out, repeat per part; trimming the start/end is just a cut from frame 0 / to the last frame, and the render gets only `CutOuts`. `MainWindow.Cuts.cs` owns the cuts (frame-exact `FrameRange`s, edited only through `CutList`: sort, clamp, merge) and the selection, and passes the cuts on as exact frame times (`CutList.ToTimeRanges`), which `Resolve` rounds straight back to the same frames. The frame on screen is `CurrentFrame()` (`MainWindow.Transport.cs`, the same rule frame stepping uses). `CutEditor` (the scissors button above the preview swaps it into the left column like a widget's settings) is only a view: typed rows are validated and reported through `CutsEdited` after a short pause (kept in the typed order, not merged, so rows don't move under the caret); its buttons and the preview's keys both go through `MainWindow.ApplyCutAction`. Any edit that would remove everything is rejected before it reaches `_cuts`. `PreviewTimeline` (a `RangeBase`; compact or expanded, see Live preview) draws everything on one seconds-to-pixels mapping: cuts red and hatched with slowly moving stripes (a ~30 Hz `DispatcherTimer` while a cut exists, skipped while that timeline is hidden - not `RequestAnimationFrame`, which redrew both timelines on every display refresh next to playback), the selection bracketed in the accent, GPS loss in amber. The preview dims a cut-out frame with a "Cut out" label (`CutScrim`), and playback skips the cut parts (`PlaybackPlan` from `OutputTimeline.NextKeptStretch`, one playback stream per kept stretch on the same decoder, audio pushed back to back the same way).

Telemetry follows the cut video: `OutputTimeline.MapFrames` processes the whole recording once (so speed/heading/smoothing stay right at every join), keeps only frames inside kept pieces, moves them onto the output's own timeline (`SampleTimeSeconds` from 0; the recording time stays in `SourceTimeSeconds`/`RecordingTimeSeconds`, used by the date/time fallback) and re-sums distance over the kept pieces only. The renderer gets those frames, so the route intro, elapsed time, distance, trip progress, map route and stats describe only what's shown; GPS wall-clock time stays real. The first frame after each cut is flagged (`DerivedFrame.StartsAfterCut`), and every drawn route - compass trail, map widget, route intro - goes through `OverlayRenderer.DrawRoute` and `RouteGeometry` (the compass/map trails cached and extended as they grow, drawn through a matrix, chunked so off-screen parts are skipped, points under half a device pixel apart left out - `SyncRoute`), which crosses a cut as `OverlaySettings.RouteAcrossCuts` says (`RouteJoin`: Gap by default, Dashed, or Straight, a line across whatever the cut-out detour went around; picked in the cut editor, live in the preview, part of the route intro card's cache key). The preview (`PreviewPlayer.SetOutputTimeline`) draws the overlay from the same mapping inside kept pieces and the plain video where something is cut out.

ffmpeg (`FfmpegPipeline`): one piece goes through `AddSourceInputs` - the segment it starts in with a plain `-ss` (video + audio), plus, only if it runs into later segments, a concat input of those (video, concat filter) and an audio-only concat list (`ConcatListWriter.WriteAudioOnly`, needs `exact_stream_id` and `-itsoffset` = the list's probed start time, see its XML comment), audio stream-copied. Several pieces go through `AddCutInputs`: each opened the same way, trimmed to its exact frame count (`trim`/`atrim`), joined with the concat filter, audio re-encoded to AAC at the source bitrate (a copy can't span the joins), and the joined video's timestamps rebuilt as `N*den/num` - without that, overlay's `shortest=1` dropped the last frame. All verified on real Osmo files (single file and a piece crossing into the next file): first frame and every join frame-exact, exact frame count, audio 0 ms off in every piece. Don't switch video to concat's own `inpoint`/`-ss` (stuck frames) or drop the audio list's `-itsoffset` (audio leads by ~0.3-0.8 s). creation_time and the timecode (`SmpteTimecode`, drop-frame aware) move to the first kept frame. A partial render doesn't copy the camera's djmd/dbgi tracks (they'd cover the whole recording).

## Render output parity

The default export must match the source's own encode 1:1 (verified field by field with ffprobe against Osmo Action 6 originals): constant bitrate at the source's rate, no B-frames, GOP measured from the source's keyframes, HEVC level and tier read from the source (`SourceProbe` - tier via `trace_headers`, ffprobe doesn't report it), `hvc1` tag, exact frame count (`overlay=...:shortest=1`, `VideoInfo.FrameCount`), `creation_time` + timecode. `RenderEncodeSettings`/`OverlaySettings` export options (NVENC preset, bitrate multiplier, hardware decoding, fast start, camera metadata) may only deviate from that when the user picks a non-default value - never change the defaults.

The overlay is drawn premultiplied (Skia has no fast path for unpremultiplied targets - ~10x slower) and converted to straight alpha for ffmpeg in `BgraAlpha`. The route-intro card is static and rendered once (`_routeIntroCard`).

ffmpeg can't mux the camera's `djmd`/`dbgi` data tracks into MP4, so "keep camera metadata" is done after ffmpeg at the box level: `Mp4CameraMetadata` (appends the tracks + moov/udta from the source) and `Mp4FastStart` (our own faststart for that case; otherwise ffmpeg's `+faststart`). Verified: the copied tracks are byte-identical to the source and `TelemetryExtraction` reads identical frames from the render. What gets kept is chosen per part (`CameraMetadataSelection`: telemetry, debug track, thumbnails/info, serial number). The camera serial number lives in exactly one place in the whole file - the string at protobuf path f1.1.5 of the first djmd sample (next to the firmware version at f1.1.6) - and unless explicitly kept (default: not kept) the whole field is removed from the protobuf - no placeholder - with the enclosing length prefixes re-encoded; the udta `©uid` box is dropped too. Verified: 0 occurrences left, every other header field and all djmd samples byte-identical.

## Repo-specific conventions

- `ProcessHelper.CreateHidden(command, args)` - always use this instead of manually building a `ProcessStartInfo` for external tools (ffmpeg/ffprobe/exiftool) - it hides the console window, redirects stdout/stderr consistently across the repo and resolves ffmpeg/ffprobe to the same install the preview's libraries come from.
- GUI colors live only in the `App.axaml` palette (`*Color`/`*Brush` resources). XAML references them with `{StaticResource ...Brush}`, C# through `Palette` (`Palette.cs`) - never a hex literal. Shared classes (`card`, `hint`, `infoLabel`, `sectionLabel`, `link` - a clickable URL TextBlock, the address in its `Tag`) are global there too; a window only adds layout overrides (margins, padding) locally. Every `ScrollViewer` has `AllowAutoHide=False` from `App.axaml`, so its bars sit beside the content instead of over it - don't turn it back on per control. The overlay's own render colors (e.g. the `#46DC6E` trail default in `PlaceholderText`) are output content, not UI, and stay as they are.
- GUI icons live only in `Icons.axaml` (filled shapes on a 16x16 grid, merged into `App.axaml`) and are shown with `IconView` (`<local:IconView Data="{StaticResource IconPlay}" Width="14" Height="14" />`, from code `Icons.Play`). IconView fills with the inherited text color, so an icon follows its button's hover/disabled state. Not `PathIcon` (stretches each shape to its own bounds, so the set wouldn't line up) and not Unicode glyphs.
- `AngleMath` (`DegToRad`/`RadToDeg`/`NormalizeDegrees`) - the only place for angle conversions; don't duplicate `* Math.PI / 180.0` in new code.
- Overlay text style: `DrawOutlined` in `OverlayRenderer` produces a thin outline + soft shadow (not a thick outline) - this is a deliberate visual decision, don't change it without an explicit request.

## Secondary tools (GUI `ToolsWindow`)

A separate window (opened from the main GUI) hosts standalone utilities unrelated to the main render flow:

- **Color tag fix** (`ColorTagFixer`): some NLEs (confirmed on Vegas Pro 2026's MainConcept muxer, HEVC/NVENC export path only - AVC/H.264 export hasn't been tested) leave `color_primaries`/`color_transfer`/`color_space` unset on export even when the project is explicitly Rec.709, causing players to guess the matrix (often wrongly) and shift colors. This remuxes just the container tags (`-c copy`, no re-encode) to force `bt709` when eligible; the fix itself supports both HEVC and H.264 streams regardless of which export path is confirmed affected.
- **Remove metadata** (`MetadataStripper`): a share-safe copy via stream copy (`-map 0:V -map 0:a?`, `-map_metadata -1`, `-fflags +bitexact`) - drops the djmd/dbgi/tmcd tracks, the MJPEG thumbnail, every tag and the header timestamps, keeps color tags, rotation, profile/level and `hvc1`. The output is written as `.partial`, re-probed and compared against the source (`Verify`), and only then moved into place. Checked on an Osmo Action 6 original: its HEVC stream has no SEI, so nothing identifying lives inside the picture data - re-check that before relying on it for another camera model.
- **Camera microphone audio** (`CameraAudioConverter`): with an external mic (DJI Mic) recording into the MP4's audio track, Osmo saves the built-in mics as a separate bare-ADTS `.AAC` next to the video, which Vegas Pro/Audacity can't open. Converts to WAV (32-bit float, the exact decoder output) or M4A (same AAC stream in an MP4 container), each verified by comparing decoded-sample MD5s against the source. No MP3 on purpose (second lossy encode). Checked on an Osmo Action 6 recording: the `.AAC` has exactly as many AAC frames as the MP4's audio track (which starts at 0 with the video), so it lines up from the start of the clip; a cross-correlation between the two mics was inconclusive (different mics/positions), so that alignment rests on the identical length.
- **Compare videos** (`CompareVideosWindow`): a hand-built comparison table (up to 6 files) of codec/resolution/bitrate/color tags side by side - not a `DataGrid`, this repo has no such dependency and the table's shape doesn't need one. This is what backs the quality-comparison claims in README.md.
- Cache/data folder management: "Open data folder" and "Clear cache" against the same `%LocalAppData%\OsmoOverlay` root that `FileSummaryCache`/`OverlayPresetStore`/`OverlaySettingsStore`/`MapTileFetcher`/NLog each independently combine for their own subfolder.
Dependency version checking/updating (installed vs. latest for ffmpeg/ffprobe/exiftool, per-tool update) is checked at startup together with the app's own update (`UpdateChecks`) and shown in `SettingsWindow`'s About tab, not in `ToolsWindow`. Its rows and update logic are `DependencyStatusRows`, backed by `DependencyVersionChecker`: installed version comes from parsing the tool's own `-version`/`-ver` output; latest version comes from whatever package manager `DependencyInstaller` already installs through - `winget show --versions` on Windows (the newest within `ExternalTool.SupportedMajorVersion` is what Update installs, a newer major is only reported), `brew info --json=v2` on macOS, and on Linux a read-only query against the local package index (`apt-cache policy`, `dnf --cacheonly list available`, or `pacman -Si`, whichever manager is present) rather than forcing a metadata refresh. That Linux path's "latest" is therefore only as fresh as the local index, not necessarily true upstream latest. Separate from `DependencyPromptWindow` (startup prompt for a *missing* tool, which only checks presence, not version).
